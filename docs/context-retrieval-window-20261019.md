# 连续检索上下文控制与命中直读

日期：2026-10-19

## 修改范围

本次仅修改 SERIES 的数据库查询、工具结果协议和模型请求投影。官方 norma SDK、原始会话、审计记录及 noa 归档不改写；无数据库迁移或前端改动。保留工作区中原有的 Planner 资产搜索权限修复及其他并行改动，不自动提交、不重启业务服务。

### 检索历史工作集

- 对任务中的 `context_search/get`、`asset_search/get`、`traffic_search/get`、`graph_overview` 生效，支持直接调用及延迟分发包装。
- 每次请求先进行当前资产权限复核，再去重，最后从新到旧保留最多 24,000 Unicode 字符的成功读取结果正文。预算按 JSON 文本计，包含正文中的转义和结构开销。
- 超额结果按完整字段缩减，携带 `history_omitted`、`history_omitted_fields` 和可执行 `reread`；原来的续页位置标明为原始页之后，避免跳过尚未展示的内容。更早的结果保留简短占位及原调用配对。
- 历史目录另限 4,000 字符，按查询合并，保留引用、命中字段、读取位置、后续页位置；同一节点的不同字段或窗口分别记录。目录超额时明确标记 `truncated`，原调用参数仍可用于重读。目录不复制证据、凭证或自由文本搜索词。
- 不淘汰写入回执、审批元数据、失败调用及批量部分失败诊断；包括概览本任务和关联任务的查询失败。`graph_overview` 重复查询也接入去重，但失败结果不覆盖成功历史。
- 不使用进程内累计计数。流式、非流式、历史恢复、默认压缩及 noa 请求都从当前历史重新生成投影，保留 noa 引用标签。没有增加总结模型请求。

此预算只控制成功检索正文及其目录，不是完整请求的 Token 硬上限。调用参数、消息结构、早期结果占位、失败诊断、系统提示及其他对话仍占空间，由现有 SDK 压缩管理。大量重复失败不能靠这项预算解决。

### Planner 态势

- 以结构化 JSON 代替整段尾部切断。所有栏目先获得目录位置，再轮流分配完整记录的正文空间；总额 24,000 字符，包含标签、说明、状态和读取入口。
- 目录包含 `shown`、`has_more`、`scope` 和读取入口；无法确定完整性时 `has_more=null`。失败用 `unavailable`，未提供用 `not_provided`，不伪装成零条。
- 超长字段通过 `omitted_fields` 指向字段读取；意图父节点和产出使用各自有效接口。关联记录的来源任务 ID 仅作来源说明，生成的读取参数沿用原调用范围。
- 冷摘要溢出 ID 最多输出 50 个，另给摘要搜索入口。既有摘要成员批量查询保持不变。
- 本次控制的是模型侧投影；原有概览查询的任务规模成本没有全部消除。例如冷摘要后台查询仍可能扫描较多候选，不能把输入长度下降解释为所有大图 SQL 都已优化。

### 搜索命中直读

- `context_search` 字符串命中新增 `match_offset`，按 Unicode 字符、从零开始；同时返回 `read`，可直接传入 `context_get`，从命中前 60 字符读取。
- 单类、混合 Worker 活动、节点正文及漏洞报告使用一致协议；JSON 对象和数组返回字段目录入口，不虚构文本偏移。
- 只有当前读取权限允许时才返回详情入口；显式本任务 ID、继承来源和跨任务权限保持原语义。后续读取仍重新检查权限。
- 固定请求说明及工具说明明确：预览、概览和省略标记不能作为不存在或未测试的证据；应按资产、意图和字段缩小查询。

### 态势目录成本

- 10 节点样本：827 → 2,712 字符，827 → 2,780 字节，新投影耗时约 186 μs。
- 1,000 节点样本：1,279 → 3,199 字符，1,279 → 3,267 字节，新投影耗时约 207 μs。
- 超长多栏目样本：旧标签投影 24,063 字符，新投影 22,615 字符，后者含完整栏目目录及读取入口；字节数 38,063 → 52,783，保留下来的中文占比不同。

目录提高可恢复性，同时增加小任务输入；不能宣称所有请求都会减少 Token。投影不增加数据库查询，概览记录采用增量大小核算，避免逐条序列化不断增长的整份 JSON。

## 工具说明按需加载（2026-11-19）

角色绑定、启用开关和参数覆盖解析完成后，按角色采用分层加载，优先保持工具可发现性和直接调用能力。

- 高频核心工具常驻简短说明及完整参数 Schema，可直接调用。共用核心包括文件、命令、上下文和资产查询；Worker/Pentest/Auto 增加资产与事实/漏洞登记、流量查询，Planner 增加派单和目标判定，MainAgent 增加调度与任务约束，Reporter 增加流量证据读取和报告保存。仅作用于已绑定工具，不新增授权。
- 常驻工具的完整原始说明、扩展 Prompt 和自定义命令配置可用 `GetToolHelp(name)` 读取；实际参数、必填字段、默认值及执行校验不缩减。已配置为延迟的工具维持原有加载和解锁规则。
- Skill 常驻名称和适用场景，每个条目最多 220 字符，不设“目录过长后只剩名称”的总量截断；正文仍在直接调用 `Skill(name)` 后加载。空场景明确标注，不编造用途。
- 低频、MCP 及其他工具保留名称，使用 `SearchExtraTools` 按名称或关键词获取完整说明和参数，再通过 `ExecuteExtraTool` 调用。工具的扩展 Prompt 同样进入发现结果。

已加载说明采用一次响应窗口：在 Schema 预算内，`SearchExtraTools` 和 `GetToolHelp` 的成功结果完整保留到紧接着的一次模型响应，后续请求中的旧发现结果改为工具名、最多 220 字符的说明摘要、完整参数 Schema 和精确重读查询；旧常驻帮助留下名称及 `GetToolHelp` 重读入口。保留的 Schema 不截断、不删除字段描述，保留嵌套结构、必填项、枚举、默认值及约束；执行仍使用原有参数校验与默认值注入。摘要明确不是完整用法，模型缺少语义、示例或参数契约时须重新查询。

搜索仍对注册表中的完整原始说明匹配关键词，重读会再次返回全文。原始会话、审计、存档及 SDK 工作历史不变，压缩仅作用于发送模型的请求视图，无需跨请求缓存，恢复后也可重建。失败结果保留；未知或截断的发现格式在刚返回时保留诊断，但不赋予执行资格，进入旧历史后替换为重读提示，避免其中的 Schema 无限驻留。noa 引用后缀保留。此适配针对当前锁定的 Norma 发现输出协议，升级 SDK 时须运行发现协议回归。

Schema 采用按最近发现顺序保留的窗口：最多 **8 个工具、Schema JSON 合计 24 KiB**。不同查询命中同一工具也只保留最新定义；旧版本不会回填。预算覆盖历史及刚返回的并行/批量发现结果，超限项改为精确重读提示。单个 Schema 本身超过 24 KiB 时，只有 `select:完整工具名` 的单工具精确查询可临时完整保留一轮，且独占窗口；下一轮成为旧历史后移除。该例外避免大 Schema 永远无法合法调用，并不截断参数。此上限仅针对发现结果中的 Schema；常驻工具、工具名称目录、调用历史及最新完整说明不计入，不能视为整个请求的总大小上限。

平台通过 `OnDemandTools` 装配的延迟工具在执行前增加硬校验：当前模型请求必须包含成功发现结果中的完整 Schema，且与当前注册工具的参数定义一致。缺失、淘汰、压缩或过期时返回精确发现入口，拒绝执行；直接猜工具名同样受限。发现本身不会更新本轮执行资格，必须等下一次请求真的携带其 Schema 后才能执行，避免同一模型响应并行“发现+猜参执行”。资格按每次请求重建，恢复会话不依赖“曾发现过”的全局缓存。原有角色授权、技能解锁、阶段限制与执行参数校验仍独立生效。显式构造的 SDK 工具不自动采用平台工具目录的此项执行约束。

相同查询且结果逐字一致的发现/帮助结果仍先去重。Skill 正文不套用此窗口，仍只去除逐字一致的重复指引。

`TestToolDocumentationWindow*` 覆盖完整发现协议、参数契约不变、旧正文缩减、并行发现、不同查询、常驻帮助重读、原始记录不变、重复投影/恢复确定性，以及流式/非流式、官方/托管会话、noa 开关组合下的发现→执行→非法参数拦截→重新发现→再次执行。

`TestToolSchemaWindow*` 覆盖 100 个工具的数量/字节预算、批量发现、单个超大 Schema 的临时例外、不同查询及版本去重、压缩/恢复后的资格重建、过期/失败/未配对/普通文本不能提供执行资格，以及流式/非流式、官方/托管会话、noa 开关下的淘汰→拒绝猜参→精确重读→恢复调用。

Skill 关联 MCP 的解锁、权限检查、默认参数和收尾阶段禁用命令仍在执行时生效，恢复会话支持直接或延迟调用的成功 Skill 记录。MCP 元数据缓存和连接生命周期保持原有逻辑；这里减少的是模型上下文，并不承诺冷启动时完全不连接 MCP。

运行时额外注入的联网、记忆和后台进程控制工具仍由 SDK 配置管理，不计入此目录的统计。`TestDefaultContextSurfaceMetrics` 比较完整目录定义与“常驻简述和完整参数 + 延迟名称 + 发现/帮助入口”的字节数，分层方案不再要求压缩到原来的 1–2 KB，不代表线上任务总 token 用量。

## 真实模型独立对照（2026-11-19）

使用本机部署实例当前默认的 `deepseek-flash`，OpenAI 协议、`thinking=enabled`、`reasoning_effort=high`。配置通过只读数据库事务加载，未运行迁移、修改生产设置或创建业务任务。API Key 不进入结果文件。

三组都使用相同的 Norma SDK 会话循环、工具注册表、参数预处理、权限与执行校验。A 为发现后持续保留说明及 Schema（保留已有相同查询去重）；B 仅让长说明过期；C 为当时的完整优化：说明过期、8 工具/24 KiB Schema 窗口及缺失/过期 Schema 的执行拦截。这是同一代码上的功能消融对照，不是不同历史二进制之间的整机比较。

固定三个任务：3 步命令→MCP→HTTP 短链；4 工具反复使用的 12 步链；12 个不同工具后回访前三个工具的 15 步链。每组各重复两次，轮换方案执行顺序，共 18 次独立正式运行。每次使用新的隔离服务和会话，同一任务/重复编号的动态票据相同。命令工具通过项目真实命令执行器启动 Python；HTTP 使用真实自定义工具构造器；MCP 使用项目实际 HTTP 客户端和初始化/发现/调用协议。后端是本机隔离合成服务，不执行生产第三方业务操作。

为了隔离本文策略影响，三组均使用非流式请求、4096 输出 token 上限、40 轮上限，并关闭自动总结/noa 和 SDK 自动重试。生产配置原为流式，因此这里不比较流式传输表现。任务通过标准为：完成全部有状态步骤，且最终返回只能从工具结果获得的隐藏回执。参数正确率按成功业务步骤/模型执行尝试计算，发现调用另计，不以 HTTP 200 或单纯 `is_error=false` 代替成功。

结果不支持把 C 作为无条件默认策略。B 总 token 比 A 减少 35.7%，请求只增加 1.9%；C 总 token 减少 18.1%，请求却增加 21.2%。在仅使用 4 个工具、窗口未满的重复任务中，C 两次运行分别发现 12 次和 11 次，而 A 每次只发现 4 次；多余发现并非单纯由容量淘汰造成。C 在本组任务的峰值上下文与 B 几乎相同。

B 的一次业务错误也揭示了只保留 Schema 的局限：`options.detail` 的 `compact/full` 都是合法枚举，但完整说明要求 `R` 开头记录必须取 `full`。模型在说明过期后用多关键词搜索未命中，随后传入 `compact`，被后端拒绝后自行纠正并完成任务。Schema 校验不能保证这类未结构化业务约束的语义正确性，关键规则应进入可保留的参数契约或明确的短说明。

成本不能用总 token 简单推断：B 未缓存输入比 A 多 31.4%，C 多 293.7%。未取得该网关输入/输出/缓存单价，不报告金额或声称一定降低账单。热缓存、工具说明短的场景，A 的缓存优势需要保留；有明显上下文压力时，B 是更值得继续优化的方向，但应解决关键规则丢失。建议下一轮保留执行拦截、明确区分“说明省略”和“Schema 淘汰”，并验证按实际上下文压力触发淘汰；在该轮测试时这些建议尚未经过真实模型验证，后续实现与对照见下一节。

生产目录只读抽样：当前启用自定义工具为 1 个 command，说明 15 字节，存储 Schema 为 `{}`（运行时会补 args）；启用 MCP 的缓存有 30 个工具，但只有 2 个保存了 Schema，共 1,521 字节，因此不能据缓存推断全部 MCP 的实际参数体积。上述合成长说明任务属于压力验证，不能替代真实业务任务的可靠性评估。每场景仅两次重复，成功率是样本描述，不是统计保证。

正式运行 336 次模型请求；另有不计入比较的 3 次短任务校准、21 次请求。本轮真实 API 合计 357 次请求，1,778,614 输入 token、31,454 输出 token，均来自 provider usage，没有本地 token 估算。逐轮请求/响应、业务评分、配置元信息及源码哈希保存在 `docs/verification/tool-live-eval-20261119/`：`manifest.json`、`catalog-sizes.json`、`paired-01/summary.json`、`paired-01/comparison.json` 和各运行的 JSON/JSONL。`analyze.py` 可重算基础聚合；comparison.json 的额外说明记录校准开销和结论。

评测入口为 `agent/live_tool_evaluation.go` 与 `server/live_tool_evaluation_test.go`，均受 `liveeval` build tag 隔离，普通构建不包含。以新输出目录运行：`ARTEX_LIVE_INSTANCE_CONFIG=/path/to/instance/config.json ARTEX_LIVE_OUT=/path/to/new-output go test -tags liveeval ./server -run '^TestLiveToolComparison$' -count=1 -v -timeout 60m`。首次运行前应让测试进程的 `SERIES_PG_DSN` 指向隔离/不可达测试地址，实例配置仅在显式的只读加载分支解析，避免 TestMain 获取生产数据库测试锁。


## B 后续优化：完整约束与压力淘汰（2026-11-19）

本轮以 B 为基础实现 D。发现结果不再仅保留开头摘要：所有独有说明、参数规则和示例保留，只折叠连续且逐字相同的长参考段落，并保留原重复次数。带代码围栏、缩进、列表和短指令的内容采取保守策略。无法确认可以压缩的独有长说明仍然保留，不按关键词猜测哪些业务规则可以删除。这意味着对非重复长文的压缩收益有限，但不再以截掉尾部规则换取较小上下文。

第一次发现就生成稳定的请求表示，使用 `contract_available` 明确表示完整 Schema 和用法约束可复用，后续调用不因“说明省略”而重新发现；原始 SDK 历史和审计记录保持不变。执行前同时校对当前请求中的 Schema、用法约束与可信工具注册表，缺失或过期则阻止执行并提供精确查询入口。已有类型、枚举、必填项、默认值、权限、Skill 解锁与收尾阶段限制继续生效。自然语言规则仍需要模型理解或业务端验证，不声称 JSON Schema 能验证所有业务含义。

Schema 不再按 8 个工具或 24 KiB 淘汰。按整份序列化请求的字节数/3估算输入 token，涵盖 system、常驻工具、发现定义和普通消息，并预留输出预算；输入估算加输出预留达到配置窗口的 80% 后，按最近发现/调用顺序淘汰到 65% 目标。估算是触发策略，不是供应商 tokenizer 的精确结果；没有窗口配置时沿用项目的 200K 默认值。淘汰状态在会话内保持，压力下降不会自动把旧定义放回上下文；精确重新发现才恢复。单个过大定义的精确查询可获得一次完整模型响应机会，模型容量检查仍具有最终约束。noa 的上下文窗口及请求视图接口保持传递。

另补充 SDK 通用输出截断处理：若成功的单工具精确查询被 SDK 截断或保存到文件，只在模型请求视图中从当前可信注册表恢复所请求的完整定义，然后继续施加压力策略和执行校验。关键词查询的残缺批次、失败结果、未配对结果和用户正文不能获得执行资格。

确定性回归覆盖：100 个 Schema 在 1M 窗口下全部保留；小窗口依据整份请求压力淘汰；system 内容也可触发压力；被淘汰定义不自动复活；完整重读恢复；说明变更/Schema 变更/截断结果校验；唯一业务规则与代码保留；重复投影稳定与审计不变；流式/非流式、托管/普通、noa 开关组合。真实 command/HTTP/MCP 隔离服务链路和全仓编译检查另行通过。
