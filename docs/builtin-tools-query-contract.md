# 内置查询工具的模型视图

本文说明 Agent 内置工具的查询投影和声明加载。原始会话、事实正文、证据、凭证及任务审批模板均保留；工具管理接口另提供加载分类与 Schema 大小预览。

## 内置工具按需声明（2026-11-20）

平台内置工具采用“先授权、高频常驻、其余按需加载、加载后稳定保留、定义自身超预算才淘汰、调用前复核”的流程。这里的加载只改变本轮模型请求的工具声明，不删除工具实现、授权或历史记录。自定义/MCP 工具继续走 `SearchExtraTools` / `ExecuteExtraTool`，保留原有业务约束、上下文压力驱动的 Schema 淘汰和执行前校验。

### 授权和常驻集合

先按角色候选集合、数据库绑定、启用状态和专项开关装配实现，再建立发现目录。Planner 的宿主能力边界会过滤 `Bash`、`http_request`、交互式 Shell 和文件写入等直接执行能力；保留 ARTEX 现有的规划、漏洞上报及证据交接流程。提示词、Skill 或历史提到工具不会授予权限。

以下是常驻规则，实际集合仍取与当前授权、可用实现的交集：

| 角色 | 常驻平台工具 |
| --- | --- |
| Worker 等执行角色 | 上下文和资产读取、提问、`record_fact`、`insert_assets`、`report_finding`、`traffic_search/get` |
| 主 Agent | 上下文和资产读取、提问、`graph_overview`、`check_target_access`、`record_fact`、`dispatch_intents`、`add_intent`、`add_hint`、`set_goals`、`set_constraints`、`list_task_assets` |
| Planner | 上下文和资产读取、提问、`graph_overview`、`check_target_access`、`list_task_assets`、`add_intent`、`prove_goal` |
| Goals | 上下文读取、提问、`set_goals`、`set_constraints`、`register_user_target` |

常驻规则复用原来的 `coreTool` 角色高频集合，并保留 `record_fact` 等既有必要能力；这不是给角色新增授权。已授权的原生 `Read`、`Bash`、`Write`、`Edit`、`MultiEdit`、`LS`、`Glob`、`Grep`、`TodoWrite` 也常驻；Planner 的能力边界优先。`tool_search` 自身常驻。Skill 目录等已有核心辅助工具继续使用原机制。

### 发现和调用

`tool_search` 支持 `query`、`mode`、`limit`、`offset`、`catalog_version`：

| mode | 行为 |
| --- | --- |
| `exact` | 精确加载完整名称；本轮已声明时返回 `already_loaded` |
| `keyword` | 按名称与说明的词项/中文片段相关度排序，额外关键词不再要求全部命中；默认加载 1 个，最多 20 个；完整名称优先、同分优先选择未声明项 |
| `catalog` | 仅分页展示获授权且就绪的目录，`query` 可为空字符串，不加载 Schema |
| `auto` | 已知名称或形似完整下划线工具名时精确查找，否则关键词查找 |

`tool_search` 的声明内提供至多 24 个已授权且就绪的非高频工具名称及短说明，帮助模型直接精确加载；该索引不包含 Schema，也不授予调用权限。激活状态变化不会改写索引，避免无谓改变缓存前缀。候选只有名称、短说明和加载状态。搜索结果不包含完整 Schema；加载成功后的**下一轮模型请求**才包含完整说明、业务约束和参数契约，然后按原工具名调用。即便搜索与执行出现在同一个模型响应中，也会拒绝尚未在该响应对应请求中声明的调用。

关键词未命中时返回目录候选，不将其表述为“没有这个能力”。目录页默认 8 项，较大的 `limit` 同时扩大页面；`next` 提供续页参数。目录版本覆盖有序结果视图、元数据与当前授权；关键词无命中后的目录候选与同一 `catalog` 视图可复用游标，避免只因模式名称改变而重读。结果视图变化返回 `catalog_changed`，要求从头读取。精确查找区分 `unauthorized`、`not_found`、`unavailable`；未授权项不会进入目录候选。

每次请求、发现和实际执行都会复核适用的授权/就绪条件；批准等待结束后再次复核。参数、任务暂停/取消、超时和操作约束仍走现有执行链路。已加载工具被禁用、解绑，或角色 Web 搜索、交互 Shell 等专项能力被撤销后，旧运行器的后续调用也会被拦截。新授权但未装配的实现需新建运行器，不通过目录凭空构造。

### 上下文压力、恢复和收尾

正文与工具定义分别管理。整个请求超过“配置上下文窗口的 80% − 输出预留”时，只投影压缩旧目录候选的说明；正文增长由现有 compaction / Noa / 容量处理负责，不因此反复移除小规模已加载工具。

按需内置定义自身的预算上限为 `min(16,000, (上下文窗口 − 输出预留) / 10)`，至少为 1；达到上限内则稳定保留，超过后按最近成功使用/发现顺序淘汰，目标降至该上限的 80%。预算统计完整定义的名称、说明和参数 Schema，按序列化字节数/3估算，不是精确 tokenizer 或计费 token。例：24,000 窗口、4,096 输出预留，对应定义上限 1,990、回落目标 1,592；百万窗口对应上限 16,000。这些阈值是 ARTEX 的兼容策略，不是 OpenAI 官方默认值。

常驻工具、宿主收尾写回工具和刚发现/刚成功使用后的紧接一轮受保护，因而预算是带保护例外的软限制，不会为凑预算裁掉必需参数。直接模式不做该淘汰。正文、必需工具或单次新加载定义本身超限时，仍需现有上下文管理和容量处理，不能靠取消执行校验解决。

会话内被淘汰的工具在压力下降后不会自动重新出现，必须重新发现；执行前的本轮声明检查仍然拦截历史参数猜测。确需淘汰时，在请求尾部附上至多 8 个当前仍获授权的退出名称及精确加载提示，不改工具目录和静态系统前缀；恢复声明或撤权后移除对应提示，原始会话不改写。各会话状态独立，静态/常驻工具维持稳定前缀，新发现工具追加在声明列表后，不按使用次数重排。没有秒级卸载定时器。

同一运行会话中的压缩保留已加载定义状态。重建运行器则依据当前保留历史中配对成功的调用/发现结果重建顺序，再经过当前授权和定义预算裁剪；若恢复材料已没有加载依据，需要重新发现，不从摘要猜参数。错误、目录浏览、未配对、重复和跨用户正文拼接的结果不会恢复加载。旧内置 Schema、压力下省略的目录长说明只从请求副本移除，加载回执仍保留供恢复使用；原始记录不变。

收尾时保留宿主允许的写回工具：`record_fact`、`insert_assets`、`report_finding`、`update_finding_report`、`set_goals`、`set_constraints`、`add_hint`、`add_task_hint`、`prove_goal`。工具仍必须已装配、已授权且未被 SDK 收尾策略禁用；不会借此恢复执行类工具。

### 设置、诊断和验证

“系统设置 → 工具”的“按需加载内置工具”对应 `builtin_tool_loading`，默认 `on_demand`。关闭后为 `direct`；角色未获授权使用 `tool_search` 时也在创建运行器时回退为直接声明模式。直接模式保留授权过滤和执行校验，不进行按需 Schema 淘汰。加载模式在新建运行器时读取。

工具卡片提供角色的常驻/按需/停用/禁止分类及配置 Schema 字节数，这是配置预览，不是某个会话的实时激活列表。开启模型录制后，请求诊断的 `active_tools` 记录该次发送给模型的实际工具名称；已有 `tools` 字段保留参数定义。

验证覆盖流式/非流式、托管/普通会话、Noa 开关的 8 种组合，以及真实 SDK 收尾、压力淘汰后的重新发现、恢复历史、执行前撤权、专项开关、直接回退、配置预览和请求诊断。服务端使用独立临时 PostgreSQL；另执行竞争检测、全仓 Go 编译、TypeScript 检查及桌面/手机宽度下的 mock 页面交互验证。本节记录工程回归结果，不作为真实模型参数准确率或 Token 节省率的测量结论；此前自定义/MCP 的真实模型对照结果仍见 `context-retrieval-window-20261019.md`。

## 列表

- `list_facts`、`list_findings`：默认 20，最多 100；返回 `facts` / `findings`、`total`、`has_more`、`next_before`。总数和分页先经过任务、来源及资产授权过滤。支持 `q`、`asset_id`，漏洞另支持 `severity`。
- `list_assets`：默认 10，最多 50；`id`、`ids`、`dsl` 三选一。默认摘要不读取认证、参数、DNS 大数组和 `extra`；不展示 URL 用户信息及查询串。详细模式最多 5 个 ID，字段组为 `identity`、`fingerprint`、`dns`、`params`、`auth`、`extra`，默认仅前两个。
- `list_worker_traces`、`search_all_worker_traces`：默认 20，最多 100；`before` 续页。继承任务仅暴露已结束意图的轨迹。
- `expand_index`：按原有代表资产规则直接查询，先授权再计数、分页；默认 20，最多 100。索引正文是摘要，完整正文通过 `expand_digest` 读取。
- 列表预算 24,000 字符；预算触发时保留完整记录并提供继续位置，不裁断序列化后的 JSON。

漏洞查找优先按 `asset_id`、`q`、`severity` 筛选；`q` 搜索全部授权可见记录的摘要，不搜索证据正文。未找到且 `has_more=true` 时，响应附 `read_hint`：保持筛选条件，用 `next_before` 作为 `before` 续页；改变筛选时清除 `before`。找到所需记录即可停止，无需自动遍历全量。查询失败报告“查询失败”，预算不足报告“尚未查完”；查完也只能说“当前授权可见记录中，该筛选条件下未找到”，不能断言目标没有漏洞或证据正文无相关内容。提示用于引导模型，不保证模型绝对遵循。

## 详情与续读

文本窗口默认 8,000、最多 24,000 字符，按 Unicode 字符计算。集合中的大字段返回明确的延期标记及 JSON Pointer；用该 `field` 继续读取。集合使用 `index` / `next_index`，文本使用 `offset` / `next_offset`。

```json
{"id":123,"field":"/evidence/poc","offset":8000}
```

上例用于 `node_detail`，字段相对节点的 payload。资产详情字段相对所选字段组，文本偏移参数名为 `text_offset`：

```json
{"id":123,"detail":true,"fields":["auth"],"field":"/auth/0/token","text_offset":8000}
```

`get_worker_output` 直接读取最新 `result`，缺少时读取最新 `text`，返回当前意图 `state` 和 `has_output`，不能把运行中输出视为已完成。数据库只返回本次请求的正文窗口。`get_worker_trace` 通过 `step_ids` 显式读取至多 5 个步骤正文，不能与关键词或摘要页游标混用。

批量详情共享响应预算，单段可能短于所请求上限；必须以实际返回的继续位置为准。所有原始数据均保留。

## 授权与历史

Planner 的可调度权限与 Worker 的执行权限分离：意图创建、领取和启动仍要求计划锚定资产已批准；运行中 Worker 可访问、登记和读取待审批资产，并写回事实、漏洞及真实测试历史，不自动批准。Worker 不再收到 pending 跳过提醒；主动封禁、撤回、删除、异常隔离及独立 Guard 仍有效。Planner 继续过滤待审批关联结果，管理视图中的 `can_schedule` 不因此变化。

Worker 新发现及访问记录存于独立的 `task_worker_asset_access`，用于主动限制时定位运行中 Worker，不写入原意图的计划锚点；这是运行归属记录，不是新的授权表。任务/意图删除时级联清理，归档恢复不重建已结束 Worker 的运行归属。只读执行投影不修改存储中的 `approval_state`；`tested=true` 与 `pending` 可以同时存在，规划覆盖度仍使用已批准资产。

- 每次模型调用前重新批量核验资产、节点和审批管理分组，包含来源关系与授权变化。
- 同一规范化只读查询的同一页，仅保留最新成功结果正文。写操作、不同页、不同筛选及失败调用不合并；工具调用与返回配对、原始 transcript 不变。
- 历史计数明确标记为快照。历史审批查询只重新核验已有分组，不重复执行旧分页和计数查询。
- 态势查询内可复用授权及来源读取结果；该对象仅存在于本次调用的 ToolSet 副本，不跨调用缓存。
- 源任务的有限窗口计数命名为 `facts_in_window` / `findings_in_window`，不能冒充全量总数。查询失败应查看 `unavailable` 或对应错误字段，不能当作零资产或无发现。

## 内置声明真实模型对照（2026-11-19 至 20）

本节保留上一轮固定闲置窗口实验的历史结论；其中“当前”“生产默认”指当时版本。最新压力驱动实现见文首，后续确认结果见下一节。

本轮结果**不支持固定两轮闲置退出作为通用默认优化**。它保住了任务完成与执行前拦截，但额外发现、重载和声明变化增加了请求及未缓存输入。六轮改善了短间隔复用，却没有改善整体未缓存消耗。上下文不紧张时，发现后保留优于这两个固定窗口；本组任务中，优化前的常驻集合仍最省请求和未缓存输入。

### 方法与边界

复用此前部署实例的默认模型，通过只读事务加载配置并校验仍为 `deepseek-flash`、OpenAI 协议、`thinking=enabled`、`reasoning_effort=high`。四组共享生产 SDK 会话、参数预处理、执行检查和实际请求投影。非流式，输出上限 4096 token，最多 50 次请求；上下文配置为 1,000,000 token，关闭自动总结、Noa 和 SDK 自动重试以隔离策略影响。没有修改生产模型或工具配置。

基线不是“所有工具完整常驻”，而是本次内置优化前的 `OnDemandTools`：角色高频工具常驻、`GetToolHelp` 可查完整帮助、其他工具走受上下文压力管理的 ExtraTools。另三组均运行当前原生发现逻辑，仅分别设置 2 轮、6 轮或本次有界会话内不按闲置淘汰。六轮和不退出仅为 `liveeval` 评测分支，生产默认仍为两轮。

采用当前 MainAgent 的 **20 个真实领域工具名称、说明和 Schema**，不增加合成长说明。业务执行替换为进程内有状态夹具；原始数据库 handler 不运行，不读写业务任务、不探测第三方目标。工具发现及调用由真实模型完成，夹具独立检查动态资产/节点编号、DSL 精确匹配、字段组、嵌套参数、预算、枚举和观察置信度。每一步只返回下一步自然语言要求；最终回执此前不可见。另用 Python 从保存的原始参数独立重算判定、用量和发现次数，不采用模型自评。

四个固定场景：3 步短任务；间隔两次上下文读取后回访资产工具的 8 步任务；间隔四次读取后回访的 12 步任务；多种工具轮换后回访的 12 步任务。各重复 3 次，轮换四组执行顺序，共 **48 次正式运行，每组 12 个任务、105 个成功业务步骤**。同一场景/重复编号共用动态数据。网关缓存无法清空，以下是该缓存环境中的实测值；不是冷缓存压测或长期可靠性保证。

两轮相对优化前，请求增加 **57.9%**，未缓存输入增加 **662.1%（为原来的 7.62 倍）**。六轮相对两轮，请求减少 10%，重复发现从 18 降至 6，但未缓存输入增加 **15.8%**。不按闲置退出相对两轮，请求减少 16.2%、未缓存输入减少 **42.5%**；与优化前相比，仍分别增加 32.3% 和 338.3%。

在两类短间隔回访场景里，六轮消除了两轮窗口的 12 次重复发现，确有收益；但多工具轮换后，两种固定窗口都会过期。多工具场景还出现较宽的多关键词查询未命中后再精确搜索、候选翻页及版本不匹配后重读。较大的搜索 `limit` 不等于真的批量加载了相同数量工具，证据中不能据此认定“加载了大量 Schema”。

初始原生声明从基线 15 个（含帮助/ExtraTools 入口）降到 4 个，但更多发现结果留在历史中，加上声明集合变化，抵消了初始节省。例：首轮多工具任务，基线最后一次请求输入 8,217 token，两轮组为 9,183 token；原始请求中后者声明确实更小，消息历史却更大。缓存命中变化是实测现象，无法在共享网关环境中把全部差值单独归因于某一种因素。

发现/执行边界仍然有效：两轮组 11 次、六轮组 5 次未声明调用均被拦截，未推进夹具。参数问题也被保留：基线和六轮各一次用 `domain=` 做要求精确匹配的查询；保留组出现一次相同语义错误、一次把 `subdomain` 填进上下文类型枚举，均纠正后完成。模型在仅看到上下文工具时也会先尝试用其读取资产，说明减少常驻能力会影响工具选择，不只是 Schema 大小。

### 建议与复算

建议保留动态授权和执行前参数/声明检查，优先恢复 `asset_search`、`asset_get` 等本平台高频能力的常驻地位；其余工具发现后在上下文充足时保持稳定，仅在实际压力下淘汰最近少用的完整定义。低成本的工具名称/短说明目录、关键词匹配和翻页提示也应改进，以减少“先选错常驻工具、再查目录”的往返。**单纯把两轮改为六轮不足以证明优化有效**；这些后续组合尚未作为新方案经过本轮验证，因此没有自动改写生产策略。

证据位于 `docs/verification/builtin-live-eval-20261119/paired-01/`：`summary.json`、`comparison.json`、逐轮请求/响应、原始夹具参数与判定、源码快照及 SHA-256、`verification.json`。`manifest.pre-run.json` 保存运行前计划；运行后只纠正了说明文字中领域工具数量从 21 到实际 20 的笔误，没有修改测试输入或代码。`../analyze.py summary.json` 可从原始证据重算并核验指标。

正式 708 次模型请求，共 4,348,366 输入、72,173 输出 token；另有未计入比较的四个短任务校准，共 31 次请求、150,972 输入、3,592 输出 token。本轮真实 API 总计 **739 次请求、4,499,338 输入、75,765 输出 token**。所有 token 均来自模型接口返回 usage；未缓存输入等于 OpenAI 总输入减缓存读取。本轮未测试自动总结、流式传输、长期上下文压力或真实业务 handler 的端到端效果。

### 验证范围、证据与结论边界

确定性回归覆盖完整请求压力（消息、系统提示、输出预留）、最近使用顺序、刚加载保护、淘汰后禁止猜参数、再次精确发现、目录权限/排名/游标、原始历史不变、恢复和直接模式；流式/非流式、托管/普通、Noa 开关的八种组合，以及动态撤权和收尾写回均通过。完成相关竞争检测、独立 PostgreSQL 下的 agent/server/llmrec 回归、全仓 Go 编译及 TypeScript 检查。最终描述修正后重新通过内置工具和参数契约回归。一次误用无数据库测试环境运行服务端数据库用例的失败日志亦保留；改用临时数据库后全部通过，临时容器已清理。

本轮真实模型任务的峰值输入低于 14,000 token，没有触发配置为百万窗口的压力淘汰；淘汰正确性来自工程回归，不能声称已测出真实模型在超长上下文下的恢复成功率。业务执行使用隔离夹具，也不代表生产 handler 的端到端成功率。本轮小样本的 100% 调用准确率不是可靠性保证，不能用一个错误的差距声称统计显著提升。

据此，**保留最终高频常驻 + 压力淘汰方案，不恢复固定两轮退出**。当前证据支持在这些常规上下文任务及当前缓存条件下，保持完成情况与调用准确率并减少请求和未缓存输入；尚未证明所有负载、冷缓存或长期压力场景都更优。实现已在当前工作区完成，未部署或修改生产配置。

证据在 `docs/verification/builtin-pressure-eval-20261120/`：`paired-01/` 保存首轮 36 次，`confirm-01/` 保存最终 24 次；各含 `summary.json`、`comparison.json`、逐轮请求/响应、业务参数及判定、`manifest.json`、源码快照和 `verification.json`。`run_paired.py` / `run_confirm.py` 保存调度方案；`analyze.py <目录>/summary.json` 独立复算全部指标和配对差值；`regressions/` 保存工程日志。两个校准任务仅用于确认初版通路，不计入正式对照。

本次 60 次正式运行共 729 次模型请求、4,912,291 输入、72,449 输出 token，其中未缓存输入 480,675。含两个初版校准任务，实际 API 总计 **747 次请求、5,042,082 输入、74,052 输出 token，未缓存输入 491,938**；详见 `usage-totals.json`。这些总数包含开销较高的两轮对照及失败后纠正的尝试，不只统计最终方案。

## 长任务真实请求压力验证（2026-11-20）

**Schema 淘汰、重新发现和校验后执行的链路通过了本组实测，但没有证实新方案在持续压力下全面优于优化前。** 两组各 48 次淘汰后回访全部恢复成功，取得完整 Schema 后首次调用均正确。新方案仍有 14 次先调用未声明工具、被拦截后才重新发现的尝试。总体未缓存输入仅减少 2.44%，请求仅少 2 次，业务调用准确率的观察值略低；上一节常规上下文下的明显收益未在本轮复现。

### 测试方式与压力边界

继续使用相同生产配置的 `deepseek-flash`，OpenAI、high、thinking enabled、输出上限 4096。生产模型的上下文配置仍为 1,000,000，生产配置和业务数据未改动。只给**隔离测试运行器的 Schema 管理器设置 24,000 的上下文预算**：完整序列化请求按字节数/3估算，超过 15,104 时触发淘汰，尝试降至 11,504。两组使用相同预算。

正文真实发送给模型，未伪造 usage、强制删除 Schema 或给工具定义填充长说明。每次 `context_get` 返回独立的 1200 字符取证摘要，每个节点编号和摘要指纹随步骤变化，避免重复查询去重。模型实际收到的单次峰值输入为 37,120 / 38,409 token，已形成数万 token 的长请求。

这验证的是**真实长请求触发应用层压力策略**，不是模型达到百万 token 极限的测试，也不是 24k 硬容量测试。为单独比较 Schema 策略，两组继续关闭自动总结、Noa 和 SDK 自动重试；真实模型仍按原窗口接收请求。正文可持续增长到测试预算以上，因此这是一种持续压力下的策略测试，不代表启用自动压缩后的完整生产长任务效果。

优化前组仍是此前冻结的原高频常驻 + ExtraTools 基线，不是两轮退出版本。为使用新长任务夹具，通过 Go overlay 重建冻结的生产策略源码，两组共用同一新增夹具和只读诊断代码。当前压力方案的生产实现与上轮最终确认一致，本轮没有边跑边调整策略、提示词或评分标准。

### 场景差异及结论

下表每格为“业务调用成功/尝试；模型请求；重复发现；未缓存输入 token”，各场景合计三次运行：

| 场景 | 优化前 | 当前压力方案 |
| --- | ---: | ---: |
| 单工具回访 | 114/121；142；12；210,751 | 114/124；142；12；188,629 |
| 多工具轮换 | 120/127；176；36；331,465 | 120/125；174；36；340,382 |

单工具回访的未缓存输入减少 **10.50%**，但业务调用准确率更低、请求数不变。多工具轮换的调用尝试和请求更少，但未缓存输入增加 **2.69%**。六对任务中，新方案四对未缓存输入较少、两对较多；三对请求更少、一对相同、两对更多。整体 2.44% 的未缓存收益不足以表述为稳定、全面的长任务优势，调用准确率差异也只有一次额外失败尝试，不能宣称统计显著。

原始请求揭示了压力持续的原因：正文占主要空间时，移除几个 Schema 仍达不到目标水位。下一次回访需要重新加载，之后又因持续压力退出。多工具轮换还伴随频繁声明变化和未缓存用量峰值；共享网关缓存内部不可见，不能把全部差异单独归因于缓存前缀。

据此，上一节的结论应限定为常规、上下文充足的任务。**本轮验证了恢复链路与执行保护，没有验证长任务下全面优于优化前。** 后续若继续优化，应分别验证淘汰提示能否减少未声明调用，以及正文压力与短期重复使用的工具是否需要协同管理；不能仅通过放宽执行校验来换取表面成功率。

## 参考 OpenAI 公开机制的兼容实现（2026-11-20）

这里借鉴公开 API 的机制，不声称获得或复刻了 ChatGPT 未公开的内部调度策略。

- OpenAI Tool Search 支持延迟加载，并把新发现的定义置于上下文末尾以保留已有缓存；公开接口限定于受支持的模型和 Responses 协议。[官方 Tool Search](https://developers.openai.com/api/docs/guides/tools-tool-search)
- 缓存指南建议保持工具定义和顺序稳定；受支持的接口可用 `allowed_tools` 控制可调用范围。[官方缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching)
- 长对话可用 compaction 保存继续执行所需状态，同时减小上下文。[官方 Compaction](https://developers.openai.com/api/docs/guides/compaction)

本机 norma 的通用 `ToolSchema` 仅含名称、说明和参数；请求没有 `defer_loading`、`additional_tools` 或 `allowed_tools` 字段。当前生产模型也是 `deepseek-flash` 的 Chat Completions 接口。因此没有伪造 OpenAI 专有消息、切换模型或把完整 Schema 藏进普通消息后允许模型猜参数；仍用真实原生函数声明和现有执行链路。

本平台的适配选择是：高频常驻、其他工具显式发现后稳定保留，新增定义追加在声明列表后；只有按需定义自身超过独立预算才淘汰。正文增长不再触发反复卸载，继续由既有上下文管理器负责。这里的“追加”是通用协议下的工具列表追加，**不等于 OpenAI 原生的上下文末尾注入**；初次加载仍可能改变缓存前缀。

预算采用可用输入空间的 10%，上限 16,000 个估算 token，降至预算的 80% 后停止淘汰；最近使用/发现、常驻和收尾保护保持不变。确需移除时只在请求尾部提供少量退出名称及重新发现提示，不改静态目录，也不放松执行检查。全部定义仍计入上下文和输入用量，缓存复用不等于它们不占空间。这些预算、保护和提示是 ARTEX 的工程选择，并非 OpenAI 官方算法。

本轮变更限于内置工具保留策略、相应提示与测试；自定义/MCP 原有执行与 Schema 管理链路保持独立。没有修改生产模型配置或部署运行实例。

### 工程验证与真实模型对照方法

确定性测试覆盖小规模定义在长正文下保持稳定、定义超预算按最近使用顺序移除、输出预留改变预算、已移除工具不能直接调用、重新发现后的下一轮保护、退出提示只显示当前授权名称及不改原始会话。新增测试实际调用 norma compactor，确认同一会话压缩后已加载定义仍可用；重建运行器仍需当前授权及可验证的历史依据。

相关竞争检测、流式/非流式和宿主/Noa 组合、独立 PostgreSQL 的动态撤权与参数契约回归、全仓编译及 TypeScript 检查均通过。临时测试数据库已清理。保存源码的验证目录作为独立 Go 模块隔离，防止不完整快照被项目编译扫描；最初因扫描快照而失败的日志也保留。

- 每次帮助调用重新读取当前绑定，核验 Bash 与命令的启用状态和角色绑定；只有本运行器装配时已可见的命令可以返回。查询失败、禁用、解绑及 Bash 撤权均关闭读取，不执行命令或解锁其他工具。Planner 无 Bash 时不获得此帮助入口。
